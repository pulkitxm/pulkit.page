Partial clones, shallow clones, and sparse checkout

Three independent Git features can turn a multi-gigabyte clone into a small, focused checkout.

03 August 2026

Recently I needed to change one file in a repository with years of history and a large collection of committed media. A normal clone would download far more data than the task required.

Git already has the tools to avoid that work. The useful part is understanding that each one controls a different dimension of the repository.

The short version

git clone --filter=blob:none --depth 1 --no-checkout --branch main <url> repo
cd repo
git sparse-checkout set --no-cone /README.md
git checkout main

What each option changes

  • --filter=blob:none leaves file contents on the server until they are needed.
  • --depth 1 downloads the latest commit instead of the full history.
  • --no-checkout prevents Git from immediately materializing every file.
  • sparse-checkout limits the working tree to the paths you choose.

Why they compose

Shallow clone cuts history, partial clone cuts file content, and sparse checkout cuts the working tree. Because they operate on separate parts of the repository, they can be combined without changing the normal commit and push workflow.
