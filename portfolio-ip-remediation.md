## Findings and prepared changes

The portfolio build previously ingested every project from the public directory README and its poster/date manifests. It generated a gallery, numbered pages, one route per project, a search index, blurred poster content, autoplay demo videos, source browsing, prompt copying, links to the original live demos, and third-party directory-download links. Public availability was effectively the publication criterion. No project rights allowlist was present.

The gallery is now a text-only review notice at `/claude-directory/`. The upstream fetch fails closed if its directive is restored, and the gallery browser bundle is excluded from new builds. No project routes, pagination, poster placeholders, search index, prompts, code browser, or downloads are generated. The general GitHub project list excludes the disputed repository so an unchanged upstream list cannot restore its old promotional description. Navigation and the Projects and Work with me pages describe the withdrawal.

The first-talk blog article retains the author's talk narrative but replaces claims promoting unrestricted reuse with the review status. It removes the launch/demo video links, embedded demo recording, promotional tweet and reply carousel. Demonstration and promotional captures listed below are deleted. Eighteen event photographs were visually inspected: the event gallery retains unrelated venue, meeting, and food photographs, while the two slides promoting repository/gallery access are removed. Unrelated portfolio work is retained. These changes do not audit or certify all unrelated portfolio content.

A new built-output guard runs before site artifacts are uploaded in Site CI. It rejects old gallery project/pagination/index outputs, generated project social cards, withdrawn capture paths, the old gallery bundle, external demo-host references, raw code/prompt/download links, and the removed video IDs. The gallery fetch regression test verifies publication stays blocked. These checks are safeguards, not a legal conclusion.

Both deployment jobs now require a manually dispatched CI run on `main` with `publish=true`. Pushes, pull requests, and scheduled guestbook updates do not deploy. Owner approval must precede that dispatch. The blog publisher now stages the checked artifact and all deletions in an isolated temporary checkout and publishes exclusively through default-mode `pukbot commit create`, after a successful dry run and a target-head race check. App-authored mode is not used because generated files exceed its per-file limit. The workflow uses an optional target-only `BLOG_PUBLISH_TOKEN`, or verifies an actual approved manual publication through its deployed source-revision receipt, matching page hashes and canonical withdrawn-URL 404/410 responses. Stale receipts, redirects, forbidden responses and network failures cannot pass. The local publisher supports the existing authenticated GitHub session, so a personal token need not be stored in CI. Read-only secret-name inspection confirmed the new token is not currently configured; the old deploy key is never used by the new path. No secret values were read or changed.
